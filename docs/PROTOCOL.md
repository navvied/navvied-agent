# Protocol v1

Transport: any ordered byte stream (stdio, WebSocket, pipe). Encoding: UTF-8, one JSON object per line (`\n`).
Peers **ignore unknown fields and unknown events**. The reference implementation is `packages/protocol`.

## Commands (front-end → engine)

| `cmd` | Fields | Notes |
|---|---|---|
| `prompt` | `text`, `qid?`, `images?`, `files?`, `effort?, `mode?`, `paths?`, `questions?` | `questions: true` is the word of `window`, said by the window that sends the prompt, so that it is there before the turn it starts; an older hub drops the field. `qid` is a client-chosen id; re-sending a known `qid` is a no-op, so a client may safely re-send anything not yet confirmed by `taken`. A prompt sent while a turn runs is folded into it. |
| `window` | `questions` | What the window that sends it can do: `true` says it draws a `question` and sends the `answer`. Send it each time a `synced` with `windows: true` arrives, and never to a hub whose `synced` lacks it (it does not know the command). See "Questions" below. |
| `cancel` | — | Stops the turn, kills running commands, denies pending approvals. |
| `approve` | `id`, `optionId`, `input?` | Answers an `approval` event. `input` is the changed command for the Edit option, or, with the Deny option, what the person wants instead: the model is then told `Not run. The person said: <text>` as the result of the step (a secret in it is hidden); a Deny without text says `The user denied this action.` as before. |
| `answer` | `id`, `answers[][]` | Answers a `question` event: for each question, the choices picked and the person's own words (an empty list skips that question). An answer to a question that already ended (it timed out) reaches the model as a normal message from the person. See "Questions" below. |
| `compact` | — | Summarise older turns now. |
| `model` | `id` | Use another of the models in `caps.models` from the next message on. The conversation carries over. |
| `effort` | `level` (`auto` or an effort) | Set the reasoning effort from the next message on. `auto` sends none. |
| `load` | `id` | Continue a saved session: the engine answers with `loaded` (the conversation in short form), and the next `prompt` goes on in it and is saved into it. Refused while a turn runs. |
| `search` | `query`, `limit?` | Look for words in what was said in the saved conversations (full-text, any language, no model; every word must be there, the last may be only a start). Answered with a `found` event for every attached window. `query` 1 to 200 characters, `limit` 1 to 50 (default 10). |
| `sessions` | none | List the saved sessions of this engine; answered with a `sessions` event, which every attached window receives. |
| `checkpoints` | — | List the code snapshots taken before each prompt. |
| `restore` | `id`, `preview?` | Put the code back as at that checkpoint. With `preview: true`, only report what would change. |
| `job.stop` | `id` | Stop one background command (a `job` event with status `running`). A finished or unknown id is ignored. |

`mode` is `ask`, `edits`, `plan`, `auto` or `bypass` (see `docs/CLI.md`: Ask first, Accept edits, Plan only, Auto, Bypass permissions). An `approval` event may carry `risk`: why it is asked even in Auto, in plain words (it cannot be undone). `effort` is `minimal`…`max`. Limits are in `LIMITS` (e.g. 1 MB of prompt text,
8 images and files together, each at most 15 MB, 100 paths). See "Attachments" below.

## Events (engine → front-end)

Every event carries `seq` (strictly increasing) and `eid` (unique).

| `ev` | Fields | Meaning |
|---|---|---|
| `loaded` | `id`, `items?` | A saved session is now the one in use (also announced to every window, so all show the same conversation). `items` is the conversation in short form: `{k: "user"\|"assistant"\|"tool", text, qid?}` (a tool is its name; `qid` is on what the person said in this program, the id the message was sent with, so a window that already has it recognises it), the last 200, each text cut at 4000 characters. A window clears its screen and shows them. |
| `found` | `query`, `items[{id,title,snippet,updated}]` | The answer to `search`: conversations that mention the words, best first, one passage each (`snippet`, the words in [brackets]). Open one with `load`. Only the window that asked should open a menu from it. |
| `sessions` | `items[{id,title,updated,messages,source?,project?}]` | The saved sessions, newest first (at most 50). `title` is what the person asked first, on one line (60 characters); `updated` is in ms since the epoch. Only a window that asked should open a menu from it. |
| `session` | `id` | The session id (first event). |
| `loaded` | `id` | A `load` succeeded. |
| `caps` | `questions?`, `steer`, `modes`, `defaultMode?`, `compact`, `checkpoints?`, `models?`, `efforts?`, `effort?`, `vision?` | What this engine can do. Show only what is real. `models` lists what can be switched to and always names the model in use as `current`: an engine with no choice announces exactly one, and so does a program (the entry of the configuration it was made for) (`id`, `name`, and optionally `brand`, `badge`, `blurb`, `locked`, `current`, `handover`: `true` on a model of the other kind than the one running, so a front-end knows before sending `{cmd:"model"}` that choosing it is a hand-over (which says its own `notice`, the only line a page says about it; a plain switch inside the same engine says its own instead, if it wants to) and left out for a model the engine switches to itself, `catalog`: for a model of navvied.com's own catalogue, the id the site lists it under (`/api/hosted/status`), whatever name the engine gives the entry, so a page matches by `catalog` and never by the shape of `id`; left out for every other model). A computer's hub lists every model there is in `models`, the engine's own and the ones of the other kind (a program beside navvied's models, navvied's models beside a program's); `{cmd:"model", id}` for one of those hands the conversation over: the hub starts the engine that runs it and the conversation goes on with what was said so far (as text, the way compaction keeps it), then says `{ev:"notice", msg:"Now using <name>. The conversation so far goes with it."}`. A reply that is being written finishes first; a model that is not available, or unknown, or a program for a chat, is refused with an `error` before anything is closed. A conversation that goes to a program continues under the id the program gives it; `efforts` the levels the current model supports (none: it has no effort setting); `effort` the level in use. `vision` says whether the model can see pictures (`false`: pictures are not sent; absent: not known, they are sent and a refusal is turned into the same message). Sent again whenever one of them changes. |
| `user` | `qid`, `text`, `images?`, `files?` | The text of a prompt the engine accepted, sent once just before its `taken` (also for a prompt folded into a running turn). `images` is only a count; `files` lists what the engine made of each attached file (no content). It lets a second window, or a reload, show the real message. A re-sent known `qid` emits nothing. |
| `taken` | `qid` | The engine started on that prompt. |
| `text` / `thought` | `text` | Reply and reasoning, streamed in pieces. |
| `thought_end` | `ms` | The model stopped thinking; `ms` is how long. Sent once per stretch of thought, only if there was one. |
| `tool` | `id`, `name`, `status`, `input?`, `output?`, `progress?`, `parent?` | One card per `id`: `running` → `done` \| `error`. |
| `plan` | `entries[{title,status,activeForm?}]` | The task list. `activeForm` is the title in the present tense, shown while the entry is in progress. |
| `question` | `id`, `questions[{question,choices?,multi?}]`, `tool?` | The agent asks the person one to four questions and waits (only when `caps.questions` is set). Answer with `answer`. |
| `usage` | `ctx`, `win`, `out` | Context tokens used / window / produced by the last call. |
| `approval` | `id`, `title`, `options[]`, `change?`, `screen?` | Ask mode: the tool waits for `approve`. `change` shows what it would do: `{tool:"Edit",file,old,new}`, `{tool:"Write",file,content}` or `{tool:"Bash",command}`; text over 20,000 characters is cut and `truncated: true` is set. |
| `plan_proposal` | `id` | Plan mode finished; the plan was streamed as `text`. |
| `phase` | `name` | `""`, `starting` or `compacting`. |
| `job` | `id`, `title`, `status` (`running`, `done`, `failed`, `stopped`), `code?`, `startedAt?`, `last?` | A command running in the background: sent when it starts and again when it ends. `startedAt` is in ms since the epoch; `last` is the last line it printed, sent when it ends. |
| `retry` | `reason`, `attempt`, `of`, `inSeconds` | A call to the model failed in a way that is worth another try (it was busy or asked to slow down, its server broke or was too slow, or the connection dropped before anything was said; a server that nobody listens on, or an unknown name, is not tried again: it is an `error` with the address) and will be made again after `inSeconds`: `attempt` is the try that comes next, out of `of` (8). Sent before each wait; the turn goes on by itself. The service's `Retry-After` is obeyed, otherwise the wait doubles each time (1 s, 2 s, 4 s … at most 30 s) with a little spread, and all the waiting is at most two minutes. A stream that had already begun to answer is not tried again. Stopping the turn ends the wait at once. When every try is used up the next model of a chain is asked, or the failure is shown as an `error`. A page may show it as a quiet line or ignore it. |
| `notice` | `msg` | Something worth telling the person that does not stop the work, such as a connected program that could not start. |
| `alive` | — | Heartbeat during long silent work. |
| `queue` | `position` | Sent by a hosting server (never by an engine) while a session waits for a free place; `1` is next. It carries no `seq`. The engine's own events follow once the session starts. |
| `checkpoints` | `items[{id,at,label,repos}]` | The reply to `checkpoints`. |
| `restore` | `id`, `preview`, `changes[{repo,path,change}]`, `undoId?` | The reply to `restore`. `change` is `revert`, `recreate` or `remove`. A real restore first saves the current state as `undoId`. |
| `done` | `stop` | The turn ended: `end_turn`, `cancelled`, `compacted`, `error`. |
| `error` | `msg` | Something failed; a `done` follows. |

## Delivery

* A front-end keeps each prompt until `taken` (or `done`/`error`) arrives, and re-sends it after a reconnect.
* A host may buffer events by `seq` and replay those after a cursor to a reconnecting front-end.

## WebSocket transport

`navvied serve --http [--port 8787] [--host 127.0.0.1] [--web <folder>]` carries the same protocol over a WebSocket, for browsers, desktop shells and phones.

* `GET /ws?token=<token>[&since=<seq>]`: upgrade to a WebSocket. One text frame is one command (client to server) or one event (server to client), the same JSON objects as on standard input/output. A wrong or missing token answers `401`; a page from another origin answers `403`.
* `since`: the last `seq` the client has already seen. The server keeps the last 5000 events of the session and replays the newer ones when a client connects, so a reload or a dropped connection loses nothing. Without `since`, everything kept is replayed. Prompts carry a `qid`, so resending one after a reconnect is safe.
* Every client of the server sees every event; a command from any client reaches the one engine.
* `GET /api/info` (token as `?token=` or `Authorization: Bearer`): `{ "version", "model", "cwd", "session" }`. `model` and `session` are `null` while no model is connected.
* The server starts without a model. Until one is configured, a `prompt` is answered with an `error` ("No model is connected. Run `navvied init`.") and a `done`. The configuration is read again every second while no model is connected, and on every `/api/info` call and command, so the moment `navvied init` finishes the server connects by itself, and clients receive the usual `session` and `caps` events. A damaged configuration is reported as "No model is connected: " followed by the reason.
* Everything else is served from `--web` (with `index.html` as the fallback for app routes), with a strict content security policy. Without `--web`, the web UI built into the program is served (it works offline once loaded: a service worker caches the static files only, never `/ws` or `/api`).
* The token is printed once in the start-up URL. Set `NAVVIED_SERVE_TOKEN` (16 characters or more) to keep it stable. On a loopback address the `Host` header must also be loopback. With `--host 0.0.0.0` the server is reachable from the network; the token is then the only protection.
* A page served from another site (for example a hosted front-end that talks to a server on the visitor's own computer) is refused by default. `--allow-origin https://site.example` (repeatable; plain origins only, no path, no wildcard) lets that site's pages open the socket and call `/api/info`: the server answers the CORS preflight, including `Access-Control-Allow-Private-Network` for browsers that ask before a public page reaches a local address. The token is still required for everything.
* Every reply carries an `x-navvied: <version>` header (exposed to allowed cross-origin pages), so a page can tell this server from any other address.

## The site's account paths on this computer

A page of navvied.com that runs on this computer's own address asks the same paths it asks of the site, and this computer answers them. Each call needs the page's own token, like every other route. This computer adds the account's token when it asks the server; the page never sees it, and nothing of the page's (cookies, its token, its origin) is passed on. Anything not listed is not found. A cloud session answers none of them (404).

* `GET /api/account/me`: the server's own record of the signed-in person; `{ "user": null }` when nobody is signed in (answered here, with no server call).
* Open paths, also answered when nobody is signed in: `GET /api/account/providers`, `GET /api/hosted/status`.
* `GET /api/hosted/session/alive`
* The cloud conversation itself: a WebSocket at `/api/hosted/session`, with the page's own token (`?token=` or the `navvied-key.` sub-protocol). Only `conversation=<id>` and `takeover=1` of its query go on; every message goes both ways as it is, and when either side ends the other does too. Refused before anything is sent when nobody is signed in or the id is not valid.
* The relay: a WebSocket at `/relay/ws`, with the page's own token the same way. The page speaks the relay's protocol itself, end to end with another computer's pairing secret, so only the frames are passed on, both ways, with the site as the origin and no account token. Refused in a cloud session.
* `GET /api/account/computers`: the server's list, with the entry that is this computer marked `"here": true` (when it has joined the account); `PATCH|DELETE /api/account/computers/<id>`
* `GET /api/account/conversations`, `GET|PATCH|DELETE /api/account/conversations/<id>`, `POST /api/account/conversations/<id>/fork`
* `GET /api/admin/hosted`, `GET /api/admin/audit`, `PUT /api/admin/models/<id>`, `PUT /api/admin/groups/<id>`, `PUT /api/admin/cloud`, `PUT /api/admin/limits`, `POST /api/admin/groups/<id>/test`

The server decides who may do what: an admin's paths answer only for an admin. A path called with another method is refused with 405; a body is at most 1 MB; a redirect of the server is never followed. Without an account, every path but the open ones answers 401.

## Connecting a model over HTTP

A page can set up a model without a terminal. All of these need the key (`Authorization: Bearer`, or the `navvied-key.` subprotocol for a socket), answer JSON, and are open to the sites the server allows. A key sent to them is written to the private configuration file (mode 0600) and is never sent back.

| Request | Body | Answer |
| --- | --- | --- |
| `GET /api/setup` | — | `{ servers: [{ name, baseUrl, models, ollama }], programs: [{ id, label, installed }], models: [{ name, label, how, current }] }`: model servers found on this computer, the programs a person can sign in to with their plan (the `label` is ready to show), and whether each is installed, and what is already connected. |
| `POST /api/setup/test` | `{ baseUrl, api?, apiKey? }` | `{ ok: true, models }` or `{ ok: false, reason }` where `reason` is `unauthorised`, `unreachable` or `no-models`. |
| `POST /api/setup/save` | `{ baseUrl, model, name?, api?, apiKey?, window?, makeDefault? }` | `{ ok: true, name, connected }`, or `{ ok: false, error }` with status 400. The engine is started again on the new model, and clients receive the usual `session` and `caps`. For `api: "ollama"` the memory is chosen from what the model supports. |
| `POST /api/setup/use` | `{ name }` | The same, for a model that is already connected; 404 for an unknown name. |

Signing in to a program (a plan) is not done over HTTP: the page tells the person to run `navvied init` in a terminal, or the desktop app does it for them.

## Attaching to a hub: what a window is given

A hub (a computer, or a hosted session) keeps what was said, so a window that comes later, or comes back, can catch up. Attaching with `since` (the last `seq` the window saw):

* `since > 0`: every event after it, in order.
* `since = 0` (a window that knows nothing, such as a page after a refresh): only the **current conversation of each kind**, from its latest `session` or `loaded` event on, plus the latest `caps` of each kind (said once, early). Older conversations the hub still remembers are not replayed: the window lists them with `sessions`.
* Either way the last line is `{"ev":"synced","windows":true,"version":"0.1.33"}` (`windows`: the hub takes a window's own word of what it can do, so a window that draws questions answers with `{"cmd":"window","questions":true}`; the version of the program that runs the hub; absent on hubs older than 0.1.34 that have `synced` at all), also when there was nothing to replay. A hub that never sends `synced` is older than 0.1.33. It has no `kind` and no `seq`; it means the window is now up to date, so a page can end its loading state on it.

## The cloud and this computer

A signed-in computer sees what the account holds in the cloud (left by hosted sessions, or put there by a person) next to its own conversations. Nothing is moved unless the person asks.

* `SessionInfo.where`: `"cloud"` for a conversation the account holds and this computer does not have; absent for one that is on this computer.
* `{ev:"importable", count}`: how many conversations wait in the cloud for this computer (said when the hub starts and whenever that changes; a signed-out computer never says it). A page shows "N conversations from the cloud can be moved to this computer".
* `{cmd:"import", ids?}`: brings the cloud's conversations (all, or the `ids`) onto this computer, as conversations of their kind, indexed, and removes them from the cloud. Answer: `{ev:"imported", count}` (`count` 0 when nothing), the updated `sessions` of each kind, and `importable`.
* `{cmd:"move", id, to}` and `{cmd:"copy", id, to}` (kind as usual): `to` is `"this"` (a conversation `where: "cloud"` is brought here; a move deletes the cloud copy once it is saved), or the id of another computer of the account (the conversation is sent through the relay, sealed, in parts of at most 100 items; the other computer saves it as a conversation of its kind and project and says `{ev:"received"}`; a move removes the source only after that; nothing is kept by the relay or the server). `to: "cloud"` is always refused: "Conversations are never sent to the cloud from a computer." A computer that is off answers "<name> is not reachable." (nothing is queued); one that does not let it in, "<name> did not allow it."; no answer in 30 seconds, "<name> did not answer in time.". Answer: `{ev:"moved", id, to, ok, copy?, msg?}` and the updated `sessions`. **Undo is a move back**: it works because the other side still has it, until the person lets go of it.
* A conversation of a computer never reaches the cloud.
* `{cmd:"receive", id, title, project?, updated, part, parts, items}` is what the sending computer says to the target (kind as usual); a page does not need it. A conversation that is already there is not replaced, and the sender is told it is there.

## Row actions: fork, archive, read and done

A hub with `caps.rowActions: true` can do these on a saved conversation (kind as usual); each answers every window with the updated `sessions`.

| Command | What it does |
|---|---|
| `{cmd:"fork", id}` | Copies it into a new saved conversation (new id, title + " (fork)", same kind, project and place: on this computer or in the cloud). Answer: `{ev:"forked", id, newId, ok, msg?}`; a page then `load`s `newId`. |
| `{cmd:"archive", id, archived}` | Hides it from the normal list, and from `search` unless `includeArchived: true`; it is kept. `{cmd:"sessions", archived:true}` lists the archived ones (`SessionInfo.archived: true`). Unarchive = `archived:false`. |
| `{cmd:"mark", id, read?, done?}` | `read:true` clears `SessionInfo.unread`, `read:false` sets it; `done` sets or clears `SessionInfo.done`. |

`SessionInfo.unread` is set by the hub when a turn ends while no window is attached, and cleared when a window `load`s the conversation or the person marks it read.

## Folders for an agent

`caps.folders` (an agent's caps only) lists the folders the computer offers to work in: `{id, name, path?, last?, current?}`: the folder the program was started in (`current`), the ones worked in lately, and the ones the person named in their own `config.json` (`"folders": [...]`; adding one happens on the computer, never from a page). A folder that is gone is not listed. `id` stands for the path and is the only way to name it: `{cmd:"new", folder:<id>}` starts a fresh conversation whose agent works there (project instructions, checkpoints and permission scopes follow it). An id the hub did not give is refused with the error "That folder is not offered by this computer."; a chat has no folder ("A chat has no folder."). `path` is for showing on the same machine; a page never sends one. `SessionInfo.project` stays the folder's name.

## Scheduled tasks

A hub with `caps.schedule: true` keeps tasks the person scheduled (in the computer's own `schedules.json`) and lists them. `caps.scheduleNote` says when they run: "Tasks run only while this computer is on and navvied is running." A computer whose program is not running does not run them; one that comes due while it was off starts once at the next chance.

| Command | What it does |
|---|---|
| `{cmd:"schedules"}` | Answered with `{ev:"schedules", items:[ScheduleInfo]}`; the same event goes to every window whenever a task changes, starts or finishes. |
| `{cmd:"schedule.add", title?, when? \| cron?, tz?, prompt, folder?, mode?}` (+ `kind:"chat"` for a chat task) | Say when with exactly one of `when` (below) or `cron` (the same as `when:{kind:"cron", cron}`). `cron` is the five fields (minute hour day month weekday; also `@hourly`, `@daily`, `@weekly`, `@monthly`). `folder` is an id of `caps.folders` (default: the current folder; a path is never taken; a chat has none). `mode`: `plan` (reads and plans, the default) or `auto` (may change files with nobody to ask; the person's permission rules still apply). At most 50. |
| `{cmd:"schedule.update", id, title?, when? \| cron?, tz?, prompt?, enabled?, mode?, folder?}` | Changes one; `enabled: false` stops it running (it stays in the list). |
| `{cmd:"schedule.remove", id}` / `{cmd:"schedule.run", id}` | Delete one / run one now (not while it is already running). |

**One shape for when.** The Schedule tool and the screens share it: `when` is `{kind:"cron", cron}` (five fields, or `@hourly`, `@daily`, `@weekly`, `@monthly`: every day, every weekday (`0 9 * * 1-5`), every week on (`0 9 * * 1`), every month on (`0 9 1 * *`)), `{kind:"every", ms, start?}` (every `ms` milliseconds, at least 60000, counted from the last start; with `start`, a time in ms since the epoch, the starts keep to the grid of `start` plus whole intervals: every 2 weeks on a friday) or `{kind:"at", at}` (once, at `at`, ms since the epoch). `tz` is the IANA time zone the cron fields and `at` are read in (`Asia/Jakarta`); absent: this computer's own. A bad form is refused: `when.kind` must be cron, every or at, `when.ms` a whole number of at least 60000, both `when` and `cron` is refused ("give when or cron, not both"), none is refused on `schedule.add`, an unknown zone answers the `error` "The task was not saved: "…" is not a time zone.". `ScheduleInfo` gives the same shape back as `when` and `tz`, so a screen shows "every 15 minutes" from `{kind:"every", ms:900000}` and never parses `cron`; `cron` stays as the timing in a few words (`0 9 * * *`, `every 15m`, `once 2026-12-01 09:00 UTC`).

`ScheduleInfo`: `{id, title, prompt, cron, when, tz?, next?, last?, lastCode?, enabled, folder?:{id,name}, kind, mode, running?}`; times are ms since the epoch, `next` is the next time it runs (none while turned off), `lastCode` 0 means the last run was fine. A problem answers with an `error` event in plain words ("That folder is not offered by this computer.", "The task was not saved: …"). What a run said is kept on the computer.

**History and missed runs.** `ScheduleInfo` also carries `missed?: {at, reason}`: the most recent due time that nothing ran at (`at`, ms since the epoch; `reason` is `off`: the computer was off or the program was not running; a client reads a reason it does not know like `off`). It is set when a run starts more than two minutes after it was due (the task then runs once, at the next chance, and the run carries `due`), and it is gone when the next run starts on time or by hand. When several due times passed, `at` is the first of them. `{cmd:"schedule.runs", id, limit?}` (`limit` 1 to 20, default 10) is answered to the asking window with `{ev:"schedule.runs", id, runs:[ScheduleRunInfo]}`, newest first (an unknown task is answered with the `error` "That task was not found."):

| Field | Meaning |
|---|---|
| `at` | When the run started, ms since the epoch. |
| `outcome` | `fine` (exit code 0), `failed` (any other exit code, or it could not start), `stopped` (cancelled before it ended), `running` (not ended yet), `missed` (a cloud job whose time came and nothing ran). |
| `due?` | When it was due, only when it started late. |
| `said?` | What it said, on one line, at most 200 characters, secrets hidden by the program's redaction; absent when it said nothing. The whole text stays in the file named by the run on the computer, which a page never reads. |

The computer's `schedules.json` keeps the newest 20 runs of each task (each with its `said`); the screens ask for at most 20. A hosted session's cloud jobs map the same shape: `/v1/schedule` `runs` (`outcome` `ok`, `failed`, `missed`, `running`; `note`) become `fine`, `failed`, `missed`, `running` and `said` (`CloudSchedule.history(id, limit?)` in the engine does it, and `runInfoOfCloud` for one run); the cloud has no `missed` field on a job, since it is never off.

## Local models: what this computer can run

`{cmd:"machine"}` is answered with `{ev:"machine", os, arch, gpus, ramMb, freeRamMb?, disk?}`: `os` is `linux`, `wsl`, `macos`, `windows` or `unknown`; each of `gpus` is `{name, vendor, kind, memoryMb?, freeMb?, driver?}` with `kind` `discrete` (memory of its own), `integrated` (shares the computer's memory), `unified` (Apple silicon: one memory, so `memoryMb` is the computer's) or `unknown`; `freeRamMb` is what a program can get now; `disk` is the free and total space of the volume the models folder (`NAVVIED_LOCAL_DIR`, else `local` in the state folder) is on, even before the folder is made. Everything is read from the system's own tools and files (`nvidia-smi`, `lspci` and the AMD driver's files on Linux and WSL, `system_profiler` on macOS, the video controllers on Windows), each with a time limit; what cannot be read is left out or `unknown`, never guessed (a card whose name does not say whether it has memory of its own is `unknown`; the memory Windows reports for a non-NVIDIA card is capped at 4 GB and is not used). In a session that is the cloud it is refused: the hardware there is the servers'.

`{cmd:"local.search", query, window?}` searches the model hub (GGUF models, the most downloaded first) and answers with `{ev:"local.found", items, notes?}`: each item is a file `{repo, page, file, quant, sizeMb, parts, gated, tools?, fit?, needMb?, gpuLayers?, window?}`. `tools` says whether the chat template of the model handles tools (the hub lists the template with the repository, so it costs no question): `true`, `false`, or left out when the hub does not say. A model without tools can only talk in the agent. `parts` is the number of files of a model that comes in several (the first is `file`); vision projectors are not models and are left out. `fit` says where it runs on this computer at the context `window` asked for (default 32768, never above what the model supports; the `window` of the item is the one the fit is for): `gpu` all in the card's memory, `ram` it needs the computer's memory (with `gpuLayers` layers on the card, 0 for none), `none` neither has room; `needMb` is the memory it takes. The fit is worked out from the file size and the cache of keys and values at that context, with the shape of the model (layers, heads kept, size of a head) read from the first bytes of one file of each repository (a Range request of 512 KB, more if the header is longer: the model's keys come before the tokenizer's long ones); a repository whose header cannot be read, or whose kind of model the formula is not proven for (attention in every layer: the Llama, Qwen, Gemma and Phi families; state-space and hybrid models are not), is still listed, with no `fit`: the fit is never said when it is not sure. A model that needs its licence accepted (`gated`) is listed only with the person's token (the one saved for the `huggingface` provider with `provider.save`: sent to the hub only, never read back); `page` is where the person reads and accepts the licence: nothing is accepted for them. The hub allows few questions without a token: when it says that few are left, the rest of the repositories are left out and `notes` says so with the seconds to the next window; a repository that could not be read is named in `notes` with the reason. Refused in a cloud session.

`{cmd:"accounts"}` answers with `{ev:"accounts", items:[{id, installed?, version?, signedIn?, email?, plan?}]}`: the navvied account (`id:"navvied"`: `signedIn`, and its `email`), then each program of the list in `presets.ts` (`ACCOUNT_PROGRAMS`: the programs a person signs in to with a plan). A program is found on the path and asked its own `--version` and its own sign-in status command; `signedIn` and what follows are said only for a program that is installed, and `email` and `plan` only when the program says them. Nothing is signed in, no browser is opened and no saved login file is read. `{cmd:"account.install", id}` runs the program's official installer (the maker's own script, or `npm install` into the person's own folder): `{ev:"account.install", id, state:"installing"|"done"|"failed", error?}` (`failed` with "That program is not known." for an id that is not in the list), then `accounts` again. One installation of a program at a time. Both are refused in a cloud session.

`{cmd:"account.login"}` signs in to the navvied account by a link (the password never reaches a page or this protocol): `{ev:"account.login", state:"waiting", url, code, expires}` (`expires` is a time in milliseconds), and the hub asks the server (`POST /api/account/device` and `/device/token`, the same flow as `/login` in the terminal) until the person has approved the code on the site. It then keeps the account the way `/login` does (the account file, the hosted models, the computer joining the account's computers), says `{ev:"account.login", state:"done", email}`, and `accounts` follows. `state` is `denied`, `expired`, `failed` (`error`) or `stopped` otherwise; a new `account.login` replaces one that waits, and `{cmd:"account.login.cancel"}` stops it. `{cmd:"account.logout"}` signs this computer out (it leaves the account's computers, the token is cancelled on the server, the account and its models are forgotten here) and `accounts` follows; "You are not signed in." when it is not. Refused in a cloud session.

`{cmd:"account.signin", id, device?}` runs the program's own browser sign-in (the one the setup runs, started through the same module), which opens on this computer: `{ev:"account.signin", id, state:"waiting", url, code?}` (`code` only with `device: true`, the sign-in with a code to enter on another device), then the program is asked its status until it reports a login, and `{state:"done"}` follows with the model entry the setup writes (the program's saved login is used by navvied itself when it can be read, else the program is run), then `accounts`. `{cmd:"account.signin.code", id, code}` gives the program a code its sign-in page showed, `{cmd:"account.signin.cancel", id}` stops waiting (and the program), and `{cmd:"account.signout", id}` takes navvied's saved sign-in for the program away (its model entry; the program's own login is left as it is), then `accounts` follows. `failed` has an `error` in words (the program is not installed, not known, gave no address, or the sign-in was not finished). Refused in a cloud session.

`{cmd:"mcp.signin", server}` signs in to a connected program on the web (an entry of `mcp` in the configuration with a `url`) that asked for it. `{ev:"mcp.signin", server, state:"needed"}` is said when a conversation connects the program and it asks for a sign-in. After the command, `{state:"waiting", server, url}` follows and the host opens `url` in a browser of this computer (or shows it). The page comes back to a loopback address of this computer, the engine trades the code for tokens (authorization code with PKCE; the program is registered by itself when it allows that, otherwise `oauth.clientId` of the entry is used) and keeps them in `mcp-auth.json` next to the configuration (mode 0600; a token is never said in an event). Then `{state:"done"}`, or `{state:"failed", reason}` in plain words, or `{state:"stopped"}`. `code` is carried for a sign-in that shows a code to enter on another device; the loopback sign-in never sets it. `{cmd:"mcp.signin.cancel", server}` stops waiting (`stopped`); nothing is waited for longer than five minutes. A conversation started after `done` connects the program by itself; one already open keeps working without it.

**What a connected program may ask of this side.** A program may ask for a model answer (`sampling/createMessage`) or put a question to the person (`elicitation/create`). Both are offered to it in the handshake only when the engine can answer them, and no new event or command is needed: they use the events that exist. Entry keys in `mcp`: `sampling` (`"ask"` the default, `"allow"`, `"off"`), `elicitation` (`"ask"` the default, `"off"`), `maxTokens` (most the model writes for one request, default 2000), `maxPerTurn` (most requests for a model in one turn, default 3).
* **A model answer.** The request runs on the model the conversation uses, with no tools and none of the conversation; the program's text is framed as text from outside, secrets are hidden in what goes in and what comes out, and at most 60,000 characters are taken. With `ask`, each request is an `approval` event whose `tool` is `mcp:<server>` and whose `title` says what is asked ("<server> asks the model to answer: <the last message, cut at 240 characters>"); its options are Allow, Allow-and-do-not-ask-again (for that program, the rest of the conversation) and Deny. In the mode that asks nothing (`bypass`) and with `allow` no question is asked. A refusal, a conversation nobody can answer in (an `approval` needs a window that can answer) and a request over the limit are errors to the program, never to the model of the conversation.
* **A question for the person.** A form (`requestedSchema`: text, number, whole number, yes/no, one or several of a list, and one level of nested object; at most 12 fields) becomes one `question` event with `tool` `mcp:<server>` (up to four fields at once, more in the next event); the first question starts with the program's name and its message. The answer is `answer` as always: an empty list is a skipped field, which takes its default unless the field looks like a secret (name, title or format `password`, `secret`, `token`, `api key`, `pin`...): a secret field is never filled in by the engine, and a form with such a required field left empty is declined. An answer that does not fit (a word for a number, a choice not in the list) is asked again with what was wrong, twice at most, then the form is declined. The program gets `accept` with the values, `decline` (the person left a required field empty, or chose Decline in a form with no fields) or `cancel` (nobody can answer now, nobody answered in time, the turn was stopped, or a program asked more than five times in one turn). What the person typed in a secret field is hidden from the model from then on, in the text any tool of a connected program returns. A question that expires is not delivered later as a message.

`{cmd:"mcp.prompts"}` answers with `{ev:"mcp.prompts", items:[{server, name, description?, arguments?:[{name, description?, required?}]}]}`: the ready-made requests the connected programs of this conversation offer. `{cmd:"mcp.prompt", server, name, args?}` fetches one with its arguments (texts by name) and runs it as the person's own request, as `{cmd:"prompt"}` does; a failure is an `error` event. The model has the same through the `mcp__prompts` tool, with the text framed as text from outside.

`{cmd:"local.recommended", window?}` answers with `{ev:"local.found", items, notes?, recommended:true}`: at most four small models to start with, each one file (the best-liked quant that fits this computer, at the context `window`, default 32768), with the same fields as a search result (`fit` is always `gpu` or `ram`, `tools` is `true`). The card comes first, then the order of a list in the program (`RECOMMENDED_MODELS` in `presets.ts`: coding or instruct models, each kept with the line of the hub that shows its template handles tools); a repository whose template no longer says it handles tools, or that does not fit, is left out, and `notes` says what could not be read. Refused in a cloud session.

`{cmd:"local.runtime"}` asks for the state of the runtime that runs models here, `{cmd:"local.runtime.install"}` fetches it and `{cmd:"local.runtime.cancel"}` stops that (what was fetched is taken away) `{cmd:"local.runtime.remove"}` takes the runtime that is installed away (every release of it; the models stay) and answers with the state `none`; it is refused with an `error` while a model runs ("A model is running. Stop it first.") or while the runtime is being fetched. The answer, and every change while it is fetched, is `{ev:"local.runtime", state, version, backend?, file?, bytes?, total?, error?}`: `none`, `installing` (`file`, `bytes` of `total`), `verifying`, `failed` (`error`, in words) or `ready` (`backend`: `cpu`, `vulkan`, `cuda12`, `cuda13` or `metal`); `version` is the release it is pinned to. The runtime is one release of its project pinned in the program: every file has the SHA-256 the release's own page gave and that was found again by downloading it; the build is chosen from `machine` (the card's own toolkit when its driver is new enough, else Vulkan for a card with memory of its own, the processor last; Apple silicon uses its graphics), and a CUDA build comes with its runtime library. The file is fetched into a folder of the program (`runtime/<release>` under the models folder, never inside the installation), the download can be taken up again where it stopped, and the disk is checked first. A file whose hash is not the pinned one is deleted and nothing is run: not the unpacking tool and not the program; the program is run once, after the hash and the unpacking, for its version, and a build that does not start is deleted again. Refused in a cloud session.

`{cmd:"local.pull", repo, file}` fetches a model file from the hub (every part of a model that comes in several), `{cmd:"local.pause", repo, file}` stops it and leaves what was fetched, `{cmd:"local.cancel", repo, file}` stops it and takes what was fetched away, `{cmd:"local.remove", repo, file}` takes the model away (its files, its entry, the folders left empty), and `{cmd:"local.models"}` asks for what is on this computer. `file` is the path of a `.gguf` file of the repository as the hub names it (no `..`, no backslash). Progress and every change of state of a file are `{ev:"local.file", repo, file, state, bytes?, total?, error?}` with `state` `downloading`, `paused`, `nodisk` (`error` says how many MB are needed and how many are free; said before a byte is fetched, for everything still to come), `failed` (`error` in words), `done`, or `idle` (nothing of it is here: after a cancel or a removal); `local.installed {items:[{repo, file, quant, sizeMb, tools?, state, bytes?, total?, error?}]}` (`tools` is read from the chat template inside the file: left out when the file does not say) lists the finished models and the ones being fetched. Fetching asks past the bytes that are there (`Range`), so a pause, a restart of the program or a lost connection costs nothing; a server that sends the whole file starts it again. Each part is proven by the SHA-256 the hub published for it (the `lfs.oid` of its tree) before it is put in its place: a part that is not that file is deleted and the model is not kept. The token of a model that needs a licence is sent to the hub only: a redirect to another address (the hub sends files from a content network) carries the range, not the token. Models are kept in `models/<owner>--<name>/` under the models folder, and written down in `models/installed.json`. Refused in a cloud session.

`{cmd:"local.run", repo, file, window?}` runs a model that is on this computer with the program's own model server, and `{cmd:"local.stop"}` stops it. One model runs at a time (running another replaces it). `{ev:"local.server", state, repo?, file?, window?, layers?, error?}` says `starting`, `running` (`window` is the context it was started with: the one asked for, else the largest usual size up to 32768 that fits in the memory this computer has free; `layers` is how many layers went to the card: all when the model fits there, as many as there is room for when it needs the computer's memory too, none for a kind of model the fit is not proven for, which also gets a modest context), `stopped`, or `failed` (`error` in words: the runtime is not fetched, the model is not here, it does not fit, the program said why it did not start, it took too long). A model that does not fit is not started. The model of a running server is in `caps.models` (flagged `handover`, with `tools` when its chat template says whether it handles tools) only while it runs; it holds no address (the server listens on 127.0.0.1 on a port asked of the system at each start, and the address is read when the model is used), and a conversation that uses it after the server stopped is refused with "<name> is not running. Start it first." `local.runtime` carries `server` (`running` or `stopped`) and a file of `local.file` is `running` while its server does. The server is started as a plain child of the program (not detached), so whatever ends the program's tree ends it; it is stopped when the hub stops and on the program's own end or a polite signal, and a note of its process (`server.json` in the models folder) lets the next start find one that a crash left behind: it is stopped only if the system names the pinned program for that process, never otherwise. It starts when the line the program prints for it (`listening on http://127.0.0.1:<port>`, read from a real run of the pinned release) is seen. Refused in a cloud session.

`{cmd:"local.ollama"}` asks whether Ollama is on this computer and answers `{ev:"local.ollama", state, baseUrl?, version?, models?}`: `missing` (nothing answers), or `ready` with the address it listens on (`OLLAMA_HOST`, else port 11434; a wildcard address is read as this computer), its version and the models it keeps, `models: [{name, tools?}]` (`tools` is whether Ollama lists `tools` among the `capabilities` of the model, left out when it does not say). `{cmd:"local.ollama.pull", model}` fetches a model by the name Ollama knows it by (`name:size`, or `hf.co/<owner>/<repo>:<quant>`) through Ollama's own pull, and `{cmd:"local.ollama.cancel", model}` stops it; Ollama keeps the layers that were fetched and takes them up at the next pull. Each change is `{ev:"local.ollama.model", model, state, bytes?, total?, error?}`: `downloading` (`bytes` of `total`, summed over the layers Ollama has named so far, so `total` can grow), `verifying`, `done` (the model is in Ollama's list, which is said again as `local.ollama`), `failed` (`error` in words) or `idle` (stopped). A reply of a model whose calls are read from its text (it takes no tools) is cut where it goes on to write the result of its own call (`<tool_response>`, `<tool_result>`, or `Result of <tool>:` at the start of a line after a call): the program gives results, so a result the model wrote is never shown or kept. Nothing is stored or checked by this program: Ollama keeps and verifies the model, and the person chooses it afterwards among the models of the server on this computer. One pull of a name at a time. Refused in a cloud session.

## Endpoints: servers of the person's own

A person can add a server of their own (an address, how it is spoken, a key, the models to use) on a computer; it is kept in the configuration file (`endpoints`, mode 0600) and never leaves the computer. `{cmd:"endpoints"}` is answered with `{ev:"endpoints", items}` (also after every change): `{id, name, baseUrl, api, key, models}` where `api` is `chat`, `responses`, `messages` or `ollama` (saved always as one of these), `models` is `[{id, window?, vision?, pdf?}]` and `key` only says that a key is saved. `{cmd:"endpoint.save", id?, name, baseUrl, api, key?, models}` keeps one (`api` may be `auto`, which is also what an absent `api` of `endpoint.models` means: the server is asked in each style and the one that answers is saved as that concrete value; if none answers nothing is saved and the error says what was tried) (without `id` a new one is made, with an id made from its name): no `key` keeps the saved key, an empty `key` removes it, a new one replaces it. Each of its models becomes an entry of the configuration that holds only the endpoint's id and the model's id (no key, no address): both are read from the endpoint whenever the model is used, and a conversation that is open uses the key as it is at each request (a removed key or endpoint refuses the next message). `{cmd:"endpoint.remove", id}` takes away the endpoint, its key and its models. `{cmd:"endpoint.models", id}` or `{cmd:"endpoint.models", baseUrl, api, key?}` asks the server for its models, from this computer (`GET /models`, or `/api/tags` for `ollama`; for `auto` the list at `/models` is asked with the key sent both ways, and its shape says whether it is the chat or the messages style, a path that names the messages style settles a list that could be either, a list whose models all say they are reached through responses means `responses`, else `chat`; then Ollama's own list), which is also how an address and a key are tried: `{ev:"endpoint.models", api, items:[{id, window?}]}` (`api` is the style asked for, or the one found for `auto`; the window is there when the server says it, and a model without one gets the engine's default), or an `error` of one sentence (key refused, server not reached, no list). The window is read from the names a server's own source or docs show on its list of models (`max_model_len`, `meta.n_ctx`, `context_length`, `limit.context`); a server that does not say it in that list is asked in the two ways the local servers have: LM Studio keeps the size a model was loaded with (`GET /api/v1/models`, `loaded_instances[].config.context_length`: a model that is not loaded has none said, so none is given); Ollama is sent the size asked for, so the window is the largest size that fits in the memory this computer has free (from `POST /api/show` for the shape of the model and `/api/tags` for its file size, one call per model, at most sixty), never above what the model supports. A server that says it nowhere gives none. A model id can always be typed. Saving or removing an endpoint, and `provider.use`, push fresh `caps` to every window at once: the models of the endpoint are in `caps.models` (flagged `handover`: choosing one hands the conversation over) or gone, with no restart. In a session that is the cloud (`--sandboxed`, or a `webProxy`) all of these are refused.

## Providers: keys of the person's own

A computer's hub keeps what a person gives a provider (a key, a region, `base`, the other fields it asks for) in its configuration file, which only its owner can read. `base` on `provider.save` is another address for the provider (a gateway or proxy of the person): https, or http for this computer only (`localhost`, `127.0.0.1`, `[::1]`), with no name, password or fragment in it, and an empty value takes it away. It replaces the provider's own address everywhere a model of the provider is made, whatever region is chosen (and a route the provider lists for a model), and a new key is tried against it. `providers` reports it as `base`. `{cmd:"providers"}` is answered with `{ev:"providers", items}` (also after every change): one item per provider that has something saved, `{id, key, region?, fields?}`, and always one for a provider that signs in with a credential file, with `credential`: whether such a file was found now. `key` only says that a key is saved; the key itself is never sent back, and neither is the value of a secret field. `{cmd:"provider.save", id, key?, region?, fields?}` keeps what it carries and leaves the rest as it was (a key left out keeps the saved key, a field sent empty is taken away); the secret travels once, in that command. A new key is first tried on the provider's own list of models: a key it refuses (401 or 403) is not saved and the answer is the `error`; a provider that cannot be asked just now still saves the key and says, in a `notice`, that it was not checked; a provider with no list, or a change without a key, saves at once. `{cmd:"provider.remove", id}` takes everything away. A model made from a provider holds no key (only the provider's id and what was chosen); the key, the fields and the address are read from what is saved whenever the model is used, so removing the provider makes its models refuse with "Add a key for <name> first." and a new key reaches every model made from it. `{cmd:"provider.models", id}` asks the provider, at its own address with the saved key, which models it has: `{ev:"provider.models", id, models, skipped?}` (sorted; for a provider whose list names a route for each model, `skipped` holds the models no spoken route reaches, each with its reason, and is left out of `models`), or an `error` saying what went wrong (no key, no region, the key refused, not reachable). `{cmd:"provider.use", id, model}` writes one model of the configuration for it (named `<id>-<model>`, with the route the provider's list gives that model, and for a provider that signs in with a credential file of the computer, the path of that file: found by the environment variable the provider's documentation names, else its well-known place; the file stays where it is, its contents are never copied, said or logged, and a provider of this kind takes no key and has no list of models to ask for) and hands the conversation over to it like any other model (the usual `notice`). An unknown provider, a region or field it does not have, and any command of these in a session that is the cloud (started with `--sandboxed`, or given a `webProxy`) is refused; any save in a Navvied Cloud session (a key of the person's own is never kept there) are refused with an `error` and nothing is written.

## Plugins: skills, tool servers and hooks

A hub with `caps.plugins: true` lists what extends the agent on the computer: skills (folders with a `SKILL.md`, the person's own and the project's), outside tool servers (`"mcp"` in `config.json`) and hooks (`"hooks"` in `config.json`). `{cmd:"plugins"}` answers `{ev:"plugins", items:[{id, kind:"skill"|"mcp"|"hook", name, description, enabled, source:"user"|"project"|"config", fromNext?}]}` (ids `skill:<name>`, `mcp:<name>`, `hook:<event>:<n>`). `{cmd:"plugin.toggle", id, enabled}` switches one: the choice is kept in the computer's own state file and the answer is the updated list to every window; **the configuration file and the skill folders are never touched**, and adding or removing one is done on the computer, never from a page. A skill follows at once; a tool server or a hook (`fromNext: true`) from the next new conversation. An id the computer does not have is refused: "That is not installed on this computer."

A hub with `caps.memory: true` keeps notes the agent suggests for the person to accept: what it wanted to save after it read text from the web (in `ask` mode), and, in `ask` mode, the lasting facts it found in the person's own messages after a turn that ended well (a preference, a convention, a name, a decision; the host's `memory.extract` setting is `rules` by default, `model` adds one bounded model call, `off` never). In the other modes such a note is written at once, marked as the agent's own, and a `notice` says so. `{cmd:"memory.pending"}` answers `{ev:"memory.pending", count, items:[{id, scope:"project"|"user", action:"add"|"replace"|"forget", text, target?, origin:"user"|"self"|"web", source:"message"|"file"|"web"|"tool", n?, at}]}`. `count` is the number of items. `source` says where the suggestion came from: the person's own message, a file, a web page or the result of a tool; `n` is the message of the conversation it was taken from (1-based, the number `Recall` reports), when it came from one. The same event is sent by itself when a turn adds suggestions. `{cmd:"memory.pending", action:"accept"|"reject", id}` keeps (with the item's `origin`) or drops one; the answer is the updated list, and an unknown id is an `error`. Nothing is kept until it is accepted.

**Plugin packages.** A plugin is a folder with `navvied-plugin.json` (name, version, description and everything it brings: skills, agents, commands, hooks, tool servers). It is installed on the computer (`navvied plugin install <folder | .tar.gz/.tgz/.tar/.zip file or address | git address> [fingerprint]`; `navvied plugin outdated [online]` and `navvied plugin update [<name> [<fingerprint>]]` check the recorded source again: an update shows the changed files, new commands and hook events and installs only with the new fingerprint), from a page only in the two steps of `plugin.install` below, and nothing in it is run by installing. The `plugins` list carries one more kind, `plugin`, with these fields on its item: `version`, `origin` (the folder, archive or address it was installed from, never with a password; for a project's plugin the folder), `hash` (sha-256 of its files, 64 hex digits: a page may show the first 12), `brings` (`{skills:[names], agents:[names], commands:[names], hooks:<count>, mcp:[server names]}`), `runs` (every command it would run: `[{what, command, source:"plugin:<name>", findings?}]`, a hook as `what: "PreToolUse (Write)"` and a tool server as `what: "tool server <name>"`; `findings` is what reading that command found, in words, such as a delete, a send to another computer, a read of keys, administrator rights, or a download run without looking; missing when nothing; it never stops an install, but a command the hard floor blocks makes the plugin unusable with that reason in `problem`), `findings` (what a scan of the text it hands to the model found, each naming its file; missing when nothing), `trusted` (a plugin of the person's own is always trusted; one that comes with a project only after the person accepted exactly those files) and, when it cannot be used, `problem` (words: damaged, changed since it was installed, not as its manifest says). `enabled` is false until the person switches it on with `plugin.toggle` (`id: "plugin:<name>"`), and it reaches the next new conversation (`fromNext`). A project plugin waits in `skill.review` as an item `trust:plugin:<name>` (`kind: "trust"`, `findings` lists its commands with their source); answering with `accept` records its hash, so a changed plugin asks again. The plugin's `commands/*.md` become custom slash commands (`/name`, or `/plugin:name`; `$ARGUMENTS` and `$1`..`$9` are filled in).

A hub with `caps.memory: true` keeps notes the agent wanted to save after it read text from the web, in `ask` mode, for the person to accept. `{cmd:"memory.pending"}` answers `{ev:"memory.pending", items:[{id, scope:"project"|"user", action:"add"|"replace"|"forget", text, target?, origin:"user"|"self"|"web", at}]}`. `{cmd:"memory.pending", action:"accept"|"reject", id}` keeps (marked `web` in the notes file) or drops one; the answer is the updated list, and an unknown id is an `error`. Nothing is kept until it is accepted.

A hub with `caps.skillReview: true` keeps what waits for the person among skills and the record of changes the agent made. `{cmd:"skill.review"}` answers `{ev:"skill.review", items:[{id, kind:"change"|"trust", name, summary, findings?}], history:[{id, name, action:"create"|"patch"|"delete", actor:"agent"|"person", at, state:"applied"|"waiting"|"rejected"|"undone"}]}`: a `change` is a change the agent made with `skills.approval` set to `ask` (or after reading web text), a `trust` item (id `trust:<name>`) is a project skill not yet accepted when `skills.trust` is `confirm`, and `findings` says in words what the scan of its text found. `{cmd:"skill.review", id, accept}` answers one (a trust answer is kept for that exact text, so a changed skill asks again). `{cmd:"skill.rollback", id?}` undoes an applied change (the latest when `id` is absent) unless the skill was changed after it; both answer with the updated `skill.review`, preceded by a `notice` (or an `error`) that says what happened.

A hub with `caps.toolList: true` lists the tools of the agent itself. `{cmd:"tools"}` answers `{ev:"tools", items, sets, backends}`. `items` are the tools, in plain words: `{name, title, about, access:"read"|"change"|"run"|"web", enabled, core, small, calls, set}` (`core` marks what coding is made of: Read, Write, Edit, Bash, Glob, Grep, so a page should warn before one is switched off; `small` says a small model is offered it without being asked; `calls` is how often it was used on this computer; `set` is the id of its set). `sets` are the cards a page shows, `{id, title, about, tools:[names], enabled, calls}`: Files & Search, Terminal & Processes, Web & Browser, Skills & Helpers, Memory & Planning. `backends` are the places the Bash tool can run commands, `{id:"local"|"docker"|"ssh", label, about, ready, using, hint?}`: `ready:false` comes with a `hint` saying what to do (install Docker, add the ssh host to `config.json`). `{cmd:"tool.toggle", name, enabled}` switches one tool, or a whole set when `name` is a set id; `{cmd:"terminal.use", backend}` chooses where commands run (refused with the hint when it is not ready). Both are kept in the computer's own state files and answered with the updated `tools` event; they reach the next new conversation. Only commands move to a container or another computer: files are still read and written on this one. A name that is not a tool or a set is refused: "That tool is not one of the agent's."

The `tools` event also carries `sandbox: {on, network, how:"bubblewrap"|"seatbelt"|"jobobject"|"none", why?}` (absent from a host that does not say): whether commands on this computer are confined, whether a confined command may use the network, what confines them here, and for `how:"none"` the reason in a few plain words (`why`, for example that `bwrap` is not installed). `{cmd:"sandbox.use", on?, network?}` changes the one or both fields given, is kept in the computer's own state, takes effect for the next command of every conversation, and is answered with the updated `tools` event. When the sandbox stops a command, the engine asks with an ordinary `approval` event whose `title` starts "Run outside the sandbox:" and whose `risk` says what was tried; there is no other new event. Docker and SSH backends are never confined.

**One switch for each tool.** `{ev:"tools"}` also carries `entries` and `categories`. `categories` are `{id, title}` in the order to show them: `work` (Work), `browse` (Browse & research), `plan` (Plan & coordinate), `memory` (Memory & knowledge), `create` (See, hear & create) and `computer` (Control the computer). `entries` are the tools a person knows by one name, each with its own switch and its approved words: `{id, category, names, title, about, on, state, calls}`. `names` are the engine's tools the entry stands for (Files & Search is Read, Write, Edit, MultiEdit, apply_patch, NotebookEdit, Glob and Grep; Terminal & Processes is Bash and the commands that go with it; Skills is Skill and SkillManage). `state` is `on`, `off`, `needs-setup` (on, but waits for something the person must connect), `soon` (the tool does not exist yet) or `unavailable-here` (the tool exists but cannot run in this place, such as the cloud) or `experimental` (off until the person switches it on: Code Execution). Memory and Session Search are two entries; media is one entry for each kind. `{cmd:"tool.toggle", name, enabled}` takes an entry id (`session-search`), the name of one of its tools (`Recall`) or, as before, the id of a set. An entry with `setup: true` has a setup to start: `{cmd:"tool.setup", id, mode?}` starts it (an id without one is answered with an error); the six media rows (Vision, Speech to Text, Text to Speech, Image Generation, Video Generation, Video Analysis) have one. `mode` is the permission mode of the conversation the person is in. The setup is told with `{ev:"tool.setup", id, state, files?, totalMb?, file?, bytes?, total?, error?}` to every window: `ask` (what will be fetched: `files` of `{name, sizeMb}` and `totalMb`; only what is not on this computer yet; nothing is fetched until `{cmd:"tool.setup.approve", id}`; every mode but `bypass` asks, never silently), then `downloading` (`file`, `bytes` of `total` over everything left to fetch), `installing` (an archive is being taken apart), `verifying` (the program is tried once), and `done` (the tool now works with nothing else to set: the `media` part of config.json names the programs and files, and the Tools list says `on`), or `failed` (`error` in words), `unavailable` (not possible on this computer: not pinned for this system yet, a cloud session, Video Analysis without ffmpeg, and Video Generation always: no engine for it runs on a computer), or `idle` (stopped by `{cmd:"tool.setup.cancel", id}`; what was fetched stays, and the next start asks past it). Every file is pinned in the program by its address, size and SHA-256 (`packages/cli/src/media-pins.ts`): a file with another hash is deleted and nothing of it is run; the downloads can be taken up again; archives are taken apart by the program's own reader (names that leave the folder, links that lead out, devices, hard links, encrypted or 64-bit zip entries and archives past their limits are refused); everything it makes is owner-only (0700 and 0600); the programs are started without a shell and without the keys of this program in their environment. Vision and Video Analysis share one setup: the runtime of the local models (see `local.runtime`, processor build) and a small model that reads pictures, run by the program's own model server only while something looks at a picture. Only Linux on a 64-bit processor has pinned builds of the other three engines today; any other system is answered `unavailable`. A tool that is off is no longer offered in any conversation, the open ones included (the engine asks at every step), is not named as available, and a call to it is refused by name with a line that says the person turned it off. The table is data (`packages/cli/src/tool-table.ts`).

**Setup progress for a screen.** Every `tool.setup` event of a fetch (`ask`, `downloading`, `installing`, `verifying`, `done`, `failed`, `idle`) also carries `steps` and `percent`; nothing above is removed or renamed. `steps` is every thing the setup fetches, in the order it is worked on: `{name, state, bytes, total}` with `state` `waiting` (not started, or stopped by `tool.setup.cancel`), `active` (being worked on, `bytes` of `total` are its own, in bytes), `done` (`bytes` equals `total`) or `failed` (the step it stopped at; `error` of the event says why, in words). The ones before the active one are done and the ones after it wait. `percent` is 0 to 100 for the whole (`bytes` of `total` of the event, rounded down): 0 at `ask`, 100 at `done`, where it stopped at `failed` and `idle`. `unavailable` has neither. A setup with nothing left to fetch has an empty `steps`. Every row that can be `needs-setup` and has `setup: true` speaks the same events: the media rows as above, and `browser` (nothing is fetched for it: `{state:"done"}` when a browser is found on this computer, otherwise `{state:"unavailable", error:"No browser was found on this computer."}`). Computer Use is set up by the desktop app's own side; it tells the fetch of its driver with `tool.setup` and id `computer`, in the same shape (see "Computer use" below).

A hub with `caps.drafts: true` keeps what the person typed and did not send, so a refresh, another window or another device finds it. `{cmd:"draft", key, text}` keeps the text for a conversation (`key` is its id) or for a new one (`key: "new"`; at most 20000 characters; empty text takes the draft away). Every window of the computer is told at once with `{ev:"drafts", items:[{key, text, updated}]}`; that event is **not** kept in what a window that attaches later is replayed, so such a window asks with `{cmd:"drafts"}` (answered to the asker with the same event). At most 100 drafts are kept, the newest, in the computer's own state file: a draft written for a conversation of this computer never leaves it. A page clears a draft by sending empty text when it sends the message.

**A message that waits.** `{ev:"queued", qid, text, images?, files?}` says a message was received and waits its turn (the agent is busy, or a program engine is still starting): every window shows it as waiting (dimmed), not only the one that sent it. It is followed by `user` and `taken` when the agent takes it. `{ev:"dropped", qids:[…]}` says waiting messages were thrown away without being taken (the person stopped the agent, or it failed): windows take them off the screen. **A model can be chosen at any time**: `{cmd:"model"}` is never refused while a reply is being written; `caps` shows the new model as current at once, the reply in progress finishes with the model it started with, and the next message uses the new one.

**Several conversations at once on one computer.** Opening another conversation (`load`, or `new`) while one is being answered does not stop it and is not refused: the one being answered goes on in the **background** and the new one is the open one. Everything a background conversation says is sent with the same events as always plus `bg: "<conversation id>"` (so a page does not draw it in the open transcript), is not kept for a window that arrives later, and ends with its `done`: the conversation is then marked unread (as when no window was looking) and its engine is let go; the conversation itself stays and can be opened. `{ev:"background", items:[{id, kind?, state:"working"|"approval"}]}` lists them (`approval`: a step waits for the person), is sent to every window whenever it changes (an empty list when the last one ends) and, when it is not empty, to a window that arrives, before `synced`. `sessions` entries carry `running: true` while a reply is being written for them, open or in the background. `{cmd:"load", id}` for a conversation that is in the background **brings it back**: every window is sent `loaded` with what was said so far and then the events of the turn so far (`taken`, text, steps, a pending `approval`), and what follows is no longer marked `bg`; the conversation that was open goes to the background if it is being answered. At most 4 may be answered in the background at once; over that the answer is `{ev:"error", msg:"Too many conversations are running. Wait for one to finish."}`. A conversation that is being answered in the background cannot be deleted. Deleting a conversation on a computer is complete: its record, saved session, search words, checkpoints, the list of files it wrote, and the text typed for it are all removed (the snapshots themselves are git objects that nothing points to any more). `cancel` stops the open one; the terminal and the program's own interrupt stop all.

## Computer use: consent, grants and turning it on

**Consent for one application.** The agent asks before it looks at or acts in an application. The question is an ordinary `approval` event whose `screen` is `{app, about, lines}`: `app` the application's name, `about` `capture` (look at its window), `input` (click, type or press keys in it) or `foreground` (bring it in front of the person), `lines` what is about to happen, one string each, at most 8 of at most 200 characters, secrets hidden: the action as the model wrote it (`capture Notes (ax)`, `click 12`, `right click at 5,6 holding shift`, `key cmd+s`, `scroll down 3`, `drag 2 to 3`) and, for typing, `type` followed by the text, a line each. `options` are the usual three: `allow` (this step), `allow_always` (this application, for the rest of the conversation; the helper remembers it) and `deny`; `tool` is the id of the step. Answered with `approve`. Where nobody can be asked the answer is no. The native side asks from inside its call: `ComputerHelper.call(call, signal, consent)` where `consent({app, about})` resolves `once`, `app` or `no`.

**Grants and the switch.** `{cmd:"computer.state"}` is answered, and sent again to every window after each command below and whenever the native side says something changed (the person granted it in the system's settings), with `{ev:"computer.state", on, step, permissions, reason?}`. `permissions` has one row for each grant: `{id:"accessibility"|"screen-recording", state:"granted"|"missing"|"not-needed"}` (`not-needed`: this system has no such grant; only macOS asks for both today, and the list is empty for `unavailable`). `step` is where turning it on stands: `install` (the driver is not on this computer; its fetch is told with `tool.setup`, id `computer`), `permissions` (some grant is `missing`), `ready` (nothing is missing: `{cmd:"computer.on", on:true}` can switch it on) or `unavailable` (a cloud session, a system without a driver, no desktop app: `reason` says why). `{cmd:"computer.permission", id}` asks the system for one grant (its own prompt, or its settings page opens); `{cmd:"computer.on", on}` is the switch (the native side must not switch it on while a grant is missing; the hub only relays, and tells the state as the native side then reports it). A hub without the desktop app answers `{on:false, step:"unavailable", permissions:[], reason}`.

What the native side must give the hub (`HubOptions.computer(changed)` returns it): `state(): Promise<ComputerState>`, `request(id): Promise<void>`, `turn(on): Promise<void>`; and it calls `changed()` when a grant or the switch changed by itself. For the fetch of the driver it sends `{ev:"tool.setup", id:"computer", ...}` as above, and for a step it implements `ComputerHelper.call(call, signal, consent, mode)`: `mode` is the conversation's permission mode at that step (`ask`, `auto`, `bypass` or `plan`), so the native side can treat looking (capture) and acting (input) differently. `ComputerPort.helper()` returns the driver while computer use is on and nothing while it is off; the engine asks once at the start of each turn (`EngineOptions.computer` may be the helper or such a function), so the `computer` tool is offered from the next turn after the switch is flipped, in the conversation that is open, and is not offered after it is turned off. The refusal `permission_missing` of a step names the grant in `screen.which` (`Accessibility` or `Screen Recording`).

## Pictures a step saved

A `tool` event that ended may carry `picture: {path, bytes, width, height, mime}`: a file the step saved, its size in bytes, its width and height in pixels (read from the file's own header) and its type (`image/jpeg`, `image/png` or `image/webp`). `MakeImage` sets it for the picture it made (`path` is the file it named; `output` is the same `Saved <path> (<size>).` as before). The Browser tool's `screenshot` sets it when the model is shown the picture: the JPEG is also saved in the tool's own folder, `<state folder>/tools/browser/shot-<time>.jpg` (the folder is owner-only; the newest 50 are kept), and `output` is the same `Screenshot of <address> (<bytes> bytes), shown to you in the next message.` as before; a model that cannot see gets the page in words and no file. The model's text never carries the path of the tool's own folder.

## Page commands: media, agents, notes, connected programs, plugins, the screen, the browser

Everything here is data: commands and events, with no words for a screen. A hub tells what it has with the `caps` flags `media`, `a2a`, `memoryNotes`, `mcpBrowse` and `pluginInstall` (the screen's `control` is a field of `computer.state`). Where it says "to the asker only", the answer goes to the window that sent the command, carries `seq` and `eid` like every event, and is **not** kept in what a window that attaches later is replayed.

**Pictures, sounds and videos.** A `tool` event that ended may carry `media: {id, kind:"image"|"audio"|"video", mime, bytes, name, width?, height?, seconds?}` next to `picture`. It is there when the step made or kept a file a page can show: a Browser `screenshot` (also saved in the tool's own folder), `MakeImage`, `Speak`, `MakeVideo`, and `Watch` for the video it looked at. `id` is 24 hex digits made by the engine, good for this program run, and `name` is the file's own name (never a path). `{cmd:"media.read", id, offset?, length?}` is answered to the asker only with `{ev:"media", id, mime, bytes, offset, data, done}`: `data` is the base64 of the bytes from `offset` (default 0), at most `length` of them (default and most 262144), `bytes` is the size of the whole file and `done` is true on the piece that reaches its end; a page asks again from `offset + length of data` until `done`. Only ids the engine gave are read: a path is not an id (the command is refused), and the shelf behind it keeps the newest 200 files, each a plain file (no link) of the user the program runs as, not empty and at most 64 MB. A file is read only if it is still the same file as when it was kept (the same place on the disk, size and time); one that was swapped or removed answers `{ev:"error", msg:"That file changed, so it is not shown."}` or `"That file is not there any more."`. A step whose result is kept out of the conversation (a capture of the screen) carries no `media`. The model's text is the same as before.

**Agents** (`caps.a2a`; not in a cloud session, which answers `error` with "This is only available on a computer, not in Navvied Cloud."). `{cmd:"a2a.list"}` answers every window with `{ev:"a2a", peers:[{name, url, token, timeoutSeconds?}], tokens:[{name, createdAt, lastUsed?}], syncSeconds}`: `peers` are the agents this computer may ask (`a2a.peers` of the configuration; `token` says whether one is set, and neither the token nor where it is kept is ever sent), `tokens` the agents that may ask this computer (`navvied a2a list`; never the token or its hash). `syncSeconds` (2) is how often the relay looks at the token file again: a token made or revoked reaches it within that time, as with `navvied a2a add|revoke`, which these commands share their code with. `{cmd:"a2a.token.add", name}` makes the token of an agent (name: letters, digits, dots, dashes, underscores, at most 32; a name that has one is refused: `"<name>" has a token already. Revoke it first to make a new one.`) and answers the asker only with `{ev:"a2a.token", name, token}`, the one time it can be read, and every window with the updated `a2a`; only its hash is kept, in the private tokens file. `{cmd:"a2a.token.revoke", name}` takes it back (`no agent is called "<name>"` when there is none) and answers `a2a`. `{cmd:"a2a.peer.add", name, url, token?, tokenEnv?, tokenFile?, timeoutSeconds?}` keeps an agent to ask (at most one of the three ways to say where its token is; the address is `http(s)://` with no name or password in it): a given `token` is sent once, written to a private file of its own (mode 0600) and never sent back, and the configuration names that file; adding a name that is there changes it and keeps the token it had when none is given. `{cmd:"a2a.peer.remove", name}` takes it away with the token file this computer made for it (a file the person named stays). Both answer `a2a`, and apply from the next new conversation.

**Notes the agent kept** (`caps.memoryNotes`). `{cmd:"memory.list", scope?:"project"|"user"}` answers `{ev:"memory.notes", items:[{id, scope, date, text, origin:"user"|"self"|"web"}]}`, the same store the Remember tool and `/memory` use (a note of every project first). `text` is what the model is shown: secrets are replaced, and a note that fails the scan (text that gives orders, hidden characters) is `[hidden: <what was found>; ask the person to check the notes file]`. `{cmd:"memory.edit", id, scope, text}` and `{cmd:"memory.forget", id, scope}` go through the same checks as the Remember tool (no secrets or orders, at most 500 characters, not a repeat of another note, the place not full): the answer is a `notice` (`Replaced for this project (id …): …`, `Forgot for …`) or an `error` (`Error:` removed), then the updated `memory.notes`; a note is named by its `id` only (`That note is gone.` otherwise), and a change by the person is marked `user`. `{cmd:"memory.extract", mode?:"off"|"rules"|"model"}` reads or sets `memory.extract` of the configuration (the default is `rules`) and answers `{ev:"memory.extract", mode}`; the rest of the file stays and it applies from the next new conversation.

**Connected programs** (`caps.mcpBrowse`; answered by the conversation's engine, so they need a model connected). `{cmd:"mcp.resources", server?}` answers `{ev:"mcp.resources", items:[{server, uri, name?, description?, mimeType?, template?}], problems?:[{server, reason}]}` (at most 200; a `template` has `{parts}` to fill in the `uri`). `{cmd:"mcp.resource", server, uri}` answers `{ev:"mcp.resource", server, uri, contents:[{uri?, mime?, bytes, text?, data?, truncated?}]}`: `text` is cut at 1 MB, `data` is base64 and only there up to 2 MB; a document that cannot be read is an `error` (`The document could not be read: …`). `{cmd:"mcp.tools", query?, server?}` answers `{ev:"mcp.tools", query, items:[{server, name, tool, description, signature}], total}`: the same ranking the model's search of tools that are not listed uses (`name` is how the model calls it, `tool` how the program names it, `signature` what a call needs), at most 50, all of one program by name when there are no words; `total` is how many tools the connected programs have. A page's search offers nothing to the model.

**Hooks.** A hook that decided something about a step is an event `{ev:"hook", event, decision, hook, source?, step?, tool?, reason?}`. `event` is the hook event (`PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `Stop`), `hook` its command, `source` where it comes from (`plugin:<name>`; absent for the person's own), `step` the `tool` event it was about (absent for the message or the end of a turn) with `tool` its name, `reason` in the hook's own words (at most 300 characters, secrets the person typed hidden). `decision` is `allowed` (it said yes; the mode and the rules still decide), `blocked`, `asked` (the person must say yes first), `changed` (it changed the input) or `added` (it gave the model more to read). It is sent before the step's answer, and a hook that says nothing says nothing. The text the model reads is the same as before.

**Installing a plugin** (`caps.pluginInstall`; not in a cloud session). `{cmd:"plugin.install", from, fingerprint?}`: `from` is a folder or an archive on this computer, or an address (`.zip`, `.tar.gz`, `.tgz`, `.tar` or git); it is read as hostile input and nothing in it is run. Without `fingerprint` nothing is installed: the answer, to the asker only, is `{ev:"plugin.install", state:"ask", from, name, version, description, hash, brings:{skills, agents, commands, hooks, mcp}, runs:[{what, command, source, findings?}], findings?}`: what it brings and every command it would run with where each comes from, which is what `navvied plugin install` shows. With the `hash` of that answer (at least its first 12 hex digits) as `fingerprint` the same files are fetched again and installed only if they are still exactly those: `{ev:"plugin.install", state:"done", …}` to the asker and the updated `plugins` to every window; the plugin is **off** until `plugin.toggle`, and a project's plugin still waits for `skill.review`. A source that is not a plugin, a changed fingerprint or any other failure is `{ev:"plugin.install", state:"failed", from, error}`; an address is shown without any name or password in it.

**Taking the screen** (the desktop app's side gives `ComputerPort.control(who)`). `{cmd:"computer.takeover"}` and `{cmd:"computer.giveback"}` answer with `computer.state`, which now has `control:"agent"|"person"` whenever `on` is true (`agent` unless the native side says otherwise). While the person has it, every step of the agent is refused with `human_has_control`; the native side calls `changed` when the person takes it by using the screen themselves. With computer use off the answer is `error` "Computer use is off.", and without a side that can hand over, `error` "Computer use cannot be taken over from here."; `computer.state` is sent either way.

**What the Browser tool saw.** Besides the step text, the Browser tool tells what happened as `{ev:"browser", tool?, what, state, …}`, where `tool` is the step: `what:"dialog"` `state:"opened"` with `type` (`alert`, `confirm`, `prompt`, `beforeunload`), `message` and `defaultPrompt?` (cut at 500 characters), and `state:"answered"` with `type` and `accepted`; `what:"download"` `state:"started"` with `name`, and `state:"done"` or `"failed"` with `name`, `bytes?`, `path?` (where it was kept) and `note?` (why it failed), each said once; `what:"upload"` `state:"asked"` when the page opened a file chooser, and `state:"done"` with `name` (the file's own name) and `bytes` when a file went in; `what:"ref"` `state:"expired"` with `ref?` (the number asked for) and `why`: `page-changed` (the page went elsewhere since the numbers were given), `gone` (the control left the page), `unknown` (no such number on this page) or `unnumbered` (nothing was numbered yet). A download or a dialog that happens between two steps is told with the step that last ran.

**What an upload approval is about.** The `approval` for a Browser `upload` carries `upload: {path, bytes, site}` next to `title` and `tool` (as `screen` does for an application): `path` is the file as the person reads it (relative to the project when inside it, `~/…` from the home folder when inside that, otherwise the full path; secrets replaced), `bytes` its size now, and `site` the origin of the page it goes to (`https://example.com`, with no path or query). It is absent when the file or the page is not known (the step then fails by itself). The title and the text the model reads are unchanged. A page needs no `caps` flag: it shows the fields when they are there.

**A turn from another agent.** A message that came in through the A2A server carries `from: {agent, name}` on `queued` and on `user` (and on the `user` item of `loaded`, for what this program watched): `name` is the name given to the agent's token on this computer (never the token) and is the one to show ("<name> is asking"); `agent` is the label the sender wrote about itself in the message's `metadata.agent` (control characters removed, at most 64 characters), or `name` when it wrote none. A message from the person has no `from`. `PromptCommand.from` is set only by the program's own A2A server; `from` in a command read from a window is dropped, so a page cannot claim it.

## Attachments

`prompt` takes `images` (`{mime, data}`) and `files` (`{name, mime, data}`, `data` is base64 without a `data:` prefix). Together they hold at most 8 items, each at most 15 MB (20 000 000 base64 characters); a prompt is valid when it has text, an image or a file. `images` is kept as it was; a picture sent as a file works the same.

What a file is, is decided by its content, never by its name or `mime` (both only label it):

| kind | what | what the model gets |
|---|---|---|
| `image` | jpg, png, webp, gif | the picture itself, when the model can see pictures |
| `text` | any UTF-8 text or code | its text |
| `pdf` | PDF | the text of its pages; the original PDF too, where the model's service reads PDFs (up to 100 pages) |
| `document` | docx, pptx, xlsx, odt, odp, ods | its text (slides, sheets and tables as plain lines) |
| `refused` | old doc, ppt, xls; audio; video; archives; programs; other pictures; anything unreadable | one line saying it was not attached and why |

The engine saves every accepted file in the session's attachment folder (never in the project) and tells the model one line per file, `attached: report.pdf (12 pages) saved at <path>`, followed by the extracted text. The text of all files together is held to the same budget as the output of a tool; when a file is longer, the line says so and the model reads the rest with `Read` on the saved path. Nothing is installed to read these formats.

Both `queued` and `user` carry `files: [{name, kind, pages?, note?}]`, in the order sent, with no content. `note` is one plain sentence and is present for every `refused` file (the reason), for a PDF with nothing to read (`no text in this PDF (scanned pages)`), and for a picture that was not sent (`this model cannot see pictures`). A refused file is not saved and is not an `error`: the rest of the prompt goes on. When some pictures were not sent, a `notice` says so once.

A model of `caps.models` may say `files: false` (left out means yes): it is closed to attachments, for example a hosted model an administrator closed. The engine then takes no file for it: every file of the prompt is `refused` with `This model does not take files here.` (the same sentence for a front-end to show when it hides the attach control), nothing is saved, the model is told the file was not attached, and one `notice` says so. Pictures sent in `images` are not files and are not affected. The model chosen for the next message decides.

`caps.vision` tells a front-end whether to offer pictures: `false` means the model cannot see them, absent means unknown. For an unknown model the picture is sent; if the service refuses it, the picture is taken out of the conversation, the model is marked as unable to see pictures for the rest of the session, and the message is the same.

## Artifacts: the files a conversation wrote

A hub with `caps.artifacts: true` keeps a list, on the computer, of the files each conversation wrote: the ones its Write and Edit steps named, and, for a chat, any file that is new or changed in its own folder after a turn (so a file a command in a sandbox made is there too). `{cmd:"artifacts", id?}` (kind as usual; `id` is a conversation) answers `{ev:"artifacts", items:[{id, conversation, name, bytes, updated, mime, path?}]}`, newest first, files that are gone left out (`path` is for showing on the same machine). `{cmd:"artifact.read", id}` answers `{ev:"artifact", id, name, mime, bytes, text? | data?, truncated?}`: `text` for text files (cut at 1 MB, then `truncated: true`), `data` (base64) for pictures (png, jpeg, gif, webp, up to 1 MB); anything else is only listed. A file is named by the `id` the hub gave, never by a path; an unknown id, or a file that is gone, is the error "That file is gone.", and other kinds, "This kind of file cannot be shown here." Nothing is kept by the server.

## Managing the list of conversations

A hub can start a new conversation and rename, delete and pin saved ones, for each kind apart. It says so with `caps.manage: true`; a page shows the controls only then. Every command answers to every window with the updated `sessions` event (of that kind, sorted pinned first, then newest).

| Command | What it does |
|---|---|
| `{cmd:"new", kind?}` | Starts a fresh conversation of that kind: the engine says `session` (and `caps`), then the list. Refused while a turn is running. |
| `{cmd:"rename", id, title, kind?}` | Gives it another title (80 characters). The title is kept next to the conversations and wins over the one made from the first message. |
| `{cmd:"remove", id, kind?}` | Deletes it here (the saved conversation, the record, the search index) and on the account. Deleting the one in use starts a new one (`session`); refused while it is running. |
| `{cmd:"pin", id, pinned, kind?}` | `SessionInfo.pinned: true` keeps it at the top. |

`caps.models` always names the model in use (one entry, `current: true`) when there is no list to switch between, so a page can show it.

## Chat and agent: two kinds of conversation

A conversation is either an **agent** (it works on a project: the folder it was started in, the shell, git, helpers, the person's permission modes) or a **chat** (a conversation with a scratch folder of its own). The two never share a conversation, a history or a folder.

* `SessionKind` = `"agent" | "chat"`. Any command may carry `kind` (which conversation it is for) and any event may carry `kind` (which conversation it belongs to). Absent means `agent`, so an older peer that never heard of it keeps working.
* `caps.kind` says what an engine is for. A chat has `modes: []`: it asks the person nothing, because it cannot reach anything of theirs.
* `SessionInfo.kind` tells the two apart in a list. A `sessions` or `search` command with a `kind` answers with that kind only (the answer carries the `kind`).
* **What a chat may use:** WebSearch and WebFetch, Read/Write/Edit/Glob/Grep in its own scratch folder and nowhere else (not by `..`, an absolute path or a link), and Remember. Where the program itself runs in a sandbox (a hosted session) it may also run commands (Bash, BashOutput, KillShell). It has no helpers, skills, browser, task list, project instructions, hooks or checkpoints.
* **What an agent may use:** everything, as before.

## Steps in detail: what a page can show for each `tool` event

A step is the series of `tool` events with one `id`. Everything below is optional and added, so a page that ignores it still works.

| To show | Where it comes from |
|---|---|
| Queued ("waiting its turn") | `queued: true` on a step that was asked for in the same go as an earlier one; a normal running event follows when it starts |
| Running, with a clock | `status: "running"` (the page times it); `live` carries what a command printed since the last event (at most every 150 ms, 200 KB in all) |
| Waiting for the person | an `approval` event whose `tool` is the step's id; its `options` are Allow, Allow-and-do-not-ask-again, and (for a command) **Edit** with `editable.value` = the command. Answer with `approve { id, optionId, input? }`: with Edit, `input` is the changed command, which is checked again against the hard limits and the rules (a refusal shows as `outcome: "blocked"`). The step then gets a new `running` event with the changed `input` (an "edited" chip) |
| Done / failed | `status: "done"` or `"error"`, with `startedAt` (when the engine began the step, milliseconds since the epoch, by the engine's own clock), `ms` (how long), `code` (exit code of a command; `null` when it did not exit) and `output` |
| How long a group of steps took | the engine's clock only: the last `startedAt + ms` minus the first `startedAt` of its steps. Never the time the events reached the page, which a relay that sends held events together makes a span of nothing; and never the sum of `ms`, which counts steps that ran side by side twice. Steps a program runs are timed the same way (from when the step was first seen to its result) |
| Output was cut | `truncated: true` |
| Came from the cache ("Cached") | `cached: true` on a step that ended: the answer was served from what was read lately, with no new visit (`WebFetch` reading a page again, or reading on with `offset`, within 15 minutes). A step that fetched the page itself has none; `Read` has no cache, so it never carries it |
| Denied, blocked, timed out, stopped, skipped, background | `outcome` on a step that ended: `denied` (the person said no), `blocked` (a hard limit, a rule or a hook), `timeout`, `stopped` (cancelled while running), `skipped` (never started because the turn was stopped), `background` (it keeps running; follow it with the `job` events), `redirected` (never started: the person sent a new message while it waited its turn, so it did not run and the new message takes its place) |
| How a step on the screen ended (`computer`) | `screen: { verdict, code?, which?, app?, next? }` on a step that ended. `verdict` is `delivered`, `unverified` (the input was sent and cannot be proven to have landed) or `refused`; `code` is the closed reason of a refusal (`background_unavailable`, `background_occluded`, `background_uipi_blocked`, `human_has_control`, `input_target_mismatch`, `permission_missing`, `blocked_by_policy`, and `stale_target`, which only the engine says: the numbers of the last capture are out of date); `which` is what is missing for `permission_missing`; `app` the application the step was about; `next` the exact next step, as the model is told it. The step's `output` is a short note, never the capture: a capture (the numbered tree and any picture) goes to the model only, is not in the saved conversation, the events or the hooks, and the newest capture replaces the one before it in what the model carries |
| Starting, Thinking, Compacting | `phase` (`starting`, `compacting`), and `thought` … `thought_end` for thinking |
| The group's line ("Ran 3 commands, read 1 file") | counted by the page from the steps' `name`s |
| Tokens of the turn | `usage.turn` = `{in, out, calls}` so far in this turn (`in` counts every call's prompt, `out` is what the model wrote, `calls` how many times it was called); the last `usage` before `done` is the total. It starts again with each turn. A model that does not report tokens leaves `out` at 0: show nothing then |
| A task list inside its group | `plan` carries `qid` (the prompt that started the turn) and `tool` (the id of the step that wrote it, a `TodoWrite` step), so a page can put the list in that group |

Not sent: a step that is reconnecting after a dropped connection (the page knows its own connection), and a "cached" mark (no tool has a cache yet; the field name is reserved as `cached: true` on a step that ended). A page should not show those states from engine events.


## Questions: the agent asks the person

When `caps.questions` is true the model has the `Ask` tool. A call becomes one `question` event: `id`, `questions` (one to four, each `{question, choices?, multi?}`; at most four short `choices`, the recommended one first; `multi` lets more than one be picked) and `tool`, the step that asked. The person may always answer in their own words, so a page shows the choices and one free field. The answer is `{"cmd":"answer","id":"…","answers":[["Postgres"],["a","b"]]}`: one list per question, in order; an empty list is a skipped question. `cancel` ends every open question.

What the model gets back is one line per question, `Q -> "answer"` (or `Q -> (no answer)`), so a skipped question is told as such.

When nobody can answer (`navvied run` without scripted answers, a scheduled run, a hosted session with no window that can answer, a helper) the call does not wait: the model is told to make a reasonable assumption, say it in its answer and go on. A window counts only when it has said it can answer, and only while it is attached: the terminal says so as it attaches; a window at the other end of a wire (a page, over the program's own socket, the relay, a cloud session or `serve --stdio`) says so itself with `window` or with `questions: true` on a prompt. Nothing that carries a window says it for it, so a program that only sends work or only listens (a scheduled run, an editor bridge without questions, the desktop app's notices) is never counted. A window that stops being able sends `{"cmd":"window","questions":false}`. A question that is already waiting stays when the last such window leaves: a window that comes is shown it and may answer, and the time below ends the wait. Behind `serve --stdio` the whole pipe is one window, so in a cloud session the word of the pages stays until the session ends. With one attached the engine waits up to the configured time (`NAVVIED_ASK_WAIT_SECONDS`, default 600); when that passes the model is told the same, and an `answer` that arrives later is delivered to it as a normal message from the person. At most three questions are asked in one turn.
